# Manual patch management

## Previous architecture

Before this change, both installers copied `agh-ui-sync.sh` to `/usr/local/bin`, wrote shell settings in `/etc/default/agh-ui-sync`, and installed/enabled `agh-ui-sync.timer`. The timer ran its oneshot service two minutes after boot and every fifteen minutes, with randomized delay. The native installer also replaced the binary in the service's `ExecStart` with `agh-launch.sh`, preserving arguments, and downloaded a UI immediately.

The sync script read the installed binary/container version, downloaded the matching `ui-vX.Y.Z` archive/checksum, compared the checksum with `build/SHA256`, and replaced `build/static` through temporary directory renames. It restarted AdGuard Home/container after changing files. Compatibility relied on `build/VERSION`, and there was no archive-member validation or recovery if restart failed. Replacing assets under the same release tag was detected by archive checksum, not publication time.

The native uninstaller already disabled/removed the timer and service, removed the service override, launcher, shell settings and UI build, and restarted the stock UI. Docker removal required recreating the container without its override first. Release builds packaged a frontend-only UI archive and a corresponding source archive containing the patcher's scripts and installers.

## New architecture

The patcher never installs updates automatically. Updates are applied only when explicitly requested by an administrator. No replacement timer or scheduled checker is installed.

`agh-patcher status` reads local version, revision and frontend health without contacting GitHub or writing a cache. `agh-patcher check` contacts the configured public GitHub repository and reports the compatible release revision without replacing files, changing services or recording state. `agh-patcher update` performs preflight, explains the change and asks for confirmation; `--yes` is the deliberate non-interactive equivalent. `agh-patcher uninstall` removes the installed tooling and returns native AdGuard Home to its stock UI (Docker must first be recreated without the override).

The installers establish manual tooling and the launcher, retire legacy scheduler artefacts, and report status/instructions. They do not download/install a frontend or restart the running service. A fresh frontend installation uses `sudo agh-patcher update` after setup. Existing version-matched patches remain in place during migration. An already-current `update` still offers confirmation-protected legacy cleanup if obsolete updater artefacts remain, without downloading/replacing the frontend or restarting AdGuard Home.

New UI archives carry a manifest with the exact supported AdGuard Home version, a frontend revision, build tooling provenance, and SHA-256 hashes for every frontend file. UI archive checksums remain the external download-integrity mechanism. The source archive includes the CLI, installers and all identity inputs. An older archive without a manifest cannot be installed by the new updater; rebuild the compatible release with the new release tooling first.

## Separate identities

The earlier PR implementation hashed README/docs/tests/installers/manager content together with the frontend patch. That could advertise a frontend update and restart AdGuard Home for a management-only change while leaving the installed host manager unchanged.

The frontend SHA-256 now includes only `patch/PATCH_BASE`, `patch/dashboard-range.patch`, and `scripts/frontend-build.sh`. The last file isolates the actual production frontend build recipe from the gate's tests and packaging. The exact supported upstream release supplies its source, webpack configuration and locked dependencies; compatibility version plus frontend revision identifies the build inputs. Release notes' `patch:` line, manifest `patch_revision`, install receipt `patch_revision` and frontend availability comparisons all refer to this identity. The field name is retained for compatibility with the existing manifest/parser. README, docs, tests, host management and installer changes are excluded.

The tooling SHA-256 separately covers the manager, launchers/retired entry point, native/Docker installers and Compose override, release manifest generator, gate/packaging driver and GitHub build workflow. Its exact input list is `TOOLING_INPUTS` in `scripts/release-manifest.py`; README/docs/tests are excluded. Release notes use `tooling:` and the UI manifest records build provenance, which is never compared to the host tooling for frontend update detection. The installer records the installed tooling revision in local configuration. Status shows this separately (unknown for configurations predating it). An administrator upgrades tooling by downloading the source archive/repository and explicitly rerunning the appropriate installer.

The release workflow compares both identities when deciding whether to republish assets, so a tooling-only change refreshes the downloadable source tooling. The CLI compares only the compatible frontend identity: a healthy same-revision frontend remains up to date and is not downloaded/replaced/restarted merely because release tooling changed. Frontend damage and confirmed legacy scheduler cleanup retain their existing repair/migration paths. File timestamps are never revision inputs.

## Safety and rollback

The CLI uses HTTPS for metadata, archives, checksums and redirects. Only the two expected asset names/URLs for the configured GitHub repository and exact compatibility tag are accepted. It downloads into a private temporary directory, verifies the published checksum, rejects traversal/absolute paths, duplicates, links, special files, unexpected entries and excessive sizes, then validates the manifest's compatibility/revision and every frontend hash. It copies regular files itself; it never calls unrestricted tar extraction over a live installation or executes downloaded scripts. Updating the host management scripts remains a separate, explicitly invoked installer operation.

Before confirmation, no live frontend, settings, service or legacy scheduler is modified. Declining (including EOF on non-interactive stdin) leaves these untouched. `--yes` explicitly authorizes mutation without prompting; this flag is not used by an installed timer/service. Status is entirely local; check reads remote release metadata without saving an availability cache.

After confirmation, an exclusive operation lock serializes setup/update/uninstall, and version/revision are checked again to detect changes during the prompt. Root-owned, non-writable management paths and symlink rejection constrain privileged writes. The verified build is staged under the configured UI parent, and the existing build is renamed to a unique backup before the staged build is renamed into place. This is two directory renames with a short possible gap, not a multi-file overwrite. Docker binds the parent UI directory, so replacement builds remain visible.

Linux durability helpers flush each staged regular file, then child directories, the stage root and its parent. The previous build is also flushed before mutation. Newly created journal/state directory entries are flushed to their parents. JSON writes flush the temporary file before rename, then fsync the containing directory. A durable `prepared` transaction journal is committed before the first live rename; old-build-to-backup and stage-to-live renames each fsync the UI parent before the following `backup_saved` or `installed` journal phase is committed.

The CLI restarts native `AdGuardHome.service` or the configured container and requires three consecutive successful running-state checks. If Docker exposes a healthcheck, it must be healthy as well. It verifies the binary version again and all installed frontend hashes before recording success. These checks confirm process/container stability and frontend integrity; they do not perform an authenticated dashboard/DNS transaction on the administrator's service. The release gate separately smoke-tests the real official binary and HTTP APIs in an isolated temporary installation.

The last successful previous build is retained as `.agh-patcher-backup-<id>` under the UI parent, with its path durably recorded in `/var/lib/agh-patcher/last-update.json`. After service/file checks, that success receipt and a `committed` journal phase are flushed before older recorded backup cleanup and journal removal; removals fsync their containing directories. On a failed swap/restart/file/commit check a `rolling_back` phase is committed before restoration; the prior build is restored, its rename is directory-fsynced, any changed success receipt is restored, and the original service is restarted/verified. A `rolled_back` journal phase is durably written before recovery metadata is removed. A first-install failure removes the new build and restarts the stock UI. A rename can succeed before its fsync fails; rollback detects that live namespace change even if the helper raised. If recovery itself fails, the CLI returns an error and preserves available journal/backup/staging material for inspection; it does not announce success. No binary, configuration, work directory or DNS/query history is copied or restored by frontend rollback.

An abrupt power loss/SIGKILL can still interrupt the pair of renames or service restart. `/var/lib/agh-patcher/transaction.json` records the exact build/stage/backup paths and last committed phase; `status` reports the interruption, and further updates refuse it. A phase can lag a completed rename if interruption occurs between parent-directory fsync and the following journal update, so inspect the actual paths as well as the phase. Recovery is never automatic.

For a `prepared`/`backup_saved`/`installed`/`rolling_back` transaction, an administrator should stop AdGuard Home and inspect whether the live build or backup holds the previous working frontend; restore a retained backup to the recorded build path where needed (or remove a partial first-install build to use stock UI). For `committed`, the new frontend and success receipt were already flushed after validation: check that build and service before choosing to keep it or restore the backup. For `rolled_back`, verify the restored build/service. Restart and verify service health, preserve rollback material until recovery is confirmed, then remove the journal and flush its parent directory (for example, use `sync` after the explicit removal). An interruption before journal creation can leave a staged directory but cannot have changed the live frontend; inspect any such unrecorded staging material before removing it. This deliberate manual recovery avoids mutating an installation during a read-only status/check.

These ordering guarantees depend on Linux filesystem/storage implementations correctly honouring file and directory `fsync`. Unsupported flushes fail the operation rather than being silently ignored; hardware write-cache faults, filesystem corruption, weak network/overlay filesystem semantics and failures during recovery can prevent durable restoration. There is no atomic multi-directory transaction, no automatic crash recovery and no guarantee that a running process stays healthy after validation. Unit tests verify flush/phase ordering and injected failure handling; they cannot simulate physical power loss.

## Migration and removal

Running the new installer explicitly disables/stops the legacy timer first, waits up to 60 seconds for an in-flight oneshot sync to finish safely, then disables/stops its service. If the old sync remains active, migration exits with the timer disabled and asks the administrator to rerun after completion; it never kills a swap midway. A completed migration removes their installed unit files and enablement links, removes `/usr/local/bin/agh-ui-sync.sh` and `/etc/default/agh-ui-sync`, and reloads systemd. It also removes exactly the known obsolete `install/systemd/agh-ui-sync.timer` and `.service` templates from the source directory used to run the installer, including files left behind by archive extraction over an older tree. It rejects symlinked source parents and preserves unrelated templates and `ui/`.

Existing custom native paths/container names/repositories are read from the old settings as data, without sourcing/executing shell code. Updates also retire installed legacy units after administrator confirmation. The repository's old `scripts/agh-ui-sync.sh` entry point is retained only as an inert failure message, so an old cron invocation of that source path cannot apply an update. Custom administrator cron jobs should be removed separately; no cron job is installed by this project. Installer migration updates tooling and preserves the existing compatible frontend without download or restart.

Uninstall retains legacy cleanup even if the new CLI was never installed. It removes the managed command, launchers, configuration/state directory, current override, recognized patcher UI, and recorded backups/staging directories. Native uninstall first removes the override/launcher and verifies a restart using the stock binary before deleting the managed frontend. Other systemd overrides and all AdGuard Home configuration/data remain. Docker uninstall requires recreation without the patcher mounts first, preventing deletion of a still-required container launcher. The downloaded source/installer directory is left for the administrator to remove separately.
